# Learning-artifact development

Use the existing checkout. Keep source taxonomy data, schemas and the original validator unchanged unless a data task is explicitly requested.

Install from this directory with bash scripts/install.sh; run npm test. Exercise changed lesson behavior with node cli.mjs generate and node cli.mjs verify, using a fresh output directory. Inspect representative screenshots with the image viewer. The package uses its own pinned Node lockfile and local Python virtual environment.

Domain state and assessment are pure and serializable; renderers and GSAP presentation do not determine truth. Record exact evidence coverage and partial claims. Unsupported topics are plans awaiting a model, not completed visualizations. A response is not learner mastery.

Use headless Blender for asset fabrication; do not make its unconfigured MCP bridge mandatory. HyperFrames outputs must pass actual render/decoded-frame checks. Do not replace missing outputs with different deliverable types.

Keep output/, .cache/, .venv/, node_modules/, and generated logs out of Git. New topic plugins need independent model fixtures and actual UI acceptance steps. Source, expert, human and device review are separate from automated validation.

## Design learning through decisions and consequences

These requirements come from the review of Little Works and Press Club. Apply the principles to the current objective; do not copy the factory metaphor or add a business simulation to unrelated subjects.

- Start with the observable learner action and the evidence that would justify the intended conclusion. Write a short contract before building the scene: decision → prediction where useful → consequence → comparison → explanation → transfer.
- Let the learner manipulate something meaningful and see what changed. In a requested 3D activity, the scene must show the causal mechanism: quantities, queues, constraints, alternatives, or spatial relationships. A decorative scene above a form is insufficient.
- Keep a coherent model across related experiments. Change one relevant condition at a time when isolating a cause, and disclose deliberate changes in rules, prices, or context. Distinguish efficient scale, capacity utilization, bottlenecks and demand instead of labelling every cost reduction “economies of scale.”
- Reveal consequences before naming the principle. Preserve useful opportunities to predict and discover; avoid headings, answer ordering, charts or feedback that supply the solution before the learner has investigated.
- Transfer requires applying a method to a changed case, with changed numbers or constraints. A nearly identical multiple-choice question alone is weak transfer evidence.

## Make assessment require the evidence claimed

- Define required contrasting observations. A turning-point lesson must include observations on both sides of the turning point; three arbitrary runs are not sufficient. Test an attempted pass using only confirming examples and reject it with useful feedback.
- Ask learners to select or compare actual observed cases when the explanation depends on that comparison. A generic correct sentence is insufficient evidence that they interpreted their own results.
- Record predictions before the run they concern. Bind them to the setup and reference observation, preserve them alongside results, and explain mismatches. Wrong predictions are opportunities to revise a model, not permanent barriers to learning.
- Vary answer positions deterministically so replay stays reproducible. Use plausible misconceptions as distractors. Do not make the first, longest or most detailed option reliably correct. Multiple choice supports bounded recognition claims; it does not establish independent explanation or mastery.
- Distinguish successful configuration, relevant observations, comparison and reasoning. A profitable setup alone need not demonstrate the mental model. Changing a setup must not silently reuse an unrelated prediction or an obsolete assessment.
- Show help and feedback use honestly. Software tests, source review, economics/expert review, learner trials and physical-device testing are separate evidence categories.

## Keep game rules and representations honest

- Every displayed score, budget and success condition needs a clear role. If runs are resettable experiments, say so. Do not present cumulative cash as survival stakes when it cannot affect success. Add genuine resource consequences only when they serve the learning contract.
- Plot measurements as measurements. Separate efficient configurations from bottlenecks, wasted inputs, idle capacity and unmet demand. Do not label an arbitrary scatter of runs a cost curve or causal relationship. Keep each point's full setup, units, quantities and result available to touch and keyboard users.
- Animations must agree with the computed model. A machine labelled idle must not visibly process goods during the represented day. Counts, queues, waste and completed output need a consistent visual encoding; label representative rather than literal quantities.
- Disclose fictional equations and simplifying assumptions without implying universal laws. Distinguish a fresh rental choice from recovering sunk investment and average cost from total cost or profit.

## Review the actual experience

- Make the first action obvious. Keep the current decision, its consequence and the next required action close together. Introduce details progressively; do not hide required evidence in an unopened panel.
- On phones, inspect the full task sequence, not only horizontal overflow. Keep the scene useful, avoid excessive dashboard scrolling, and bring new questions/results into view without stealing focus during an unfinished interaction. Compact summaries and expandable detail should preserve access to all relevant evidence.
- Provide touch and keyboard equivalents for scene actions, readable labels, adequate targets, reduced motion, focus continuity and deterministic seek/reset.
- Run adversarial learning paths as well as the intended solution: missing contrast, wrong predictions, misleading comparisons, changed setups, answer-position shortcuts, exhausted experiments and retries. Exercise those paths through real UI controls at desktop and phone widths when mechanics change.
- Inspect screenshots of initial, changed, failed, successful and transfer states. Passing automated tests establishes implemented behavior, not engaging design or learning effectiveness. Report remaining limits and preserve separate learner/device review status.
